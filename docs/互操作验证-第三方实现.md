# 互操作验证：与第三方开源自定义终端实现对照

**目的**：用**独立实现**验证本仓库的通信协议实现是否正确（编解码、字段编号、线格式），
并确认 RM2027 与上一赛季协议中**未修改的部分**能否跨实现互通。

本次共验证了 **3 个第三方实现**（RM2026 协议）：JFCY2718（TS/React，完整可运行）、
ACE-Algorithm（C++/Qt，按其 proto 验证）、ClearWei/RM26_Client（Python/Qt，按其生成的 pb2 验证）。

**结论摘要**

1. **没有可用的 RM2027 第三方开源实现**：2027 协议 V1.0.0 于 2026-10-29 才发布，公开仓库均早于该日期；
   唯一标注 RM2027 的项目明确声明「官方协议未到位时不猜测字段」，只做模拟接口。
2. 改用 **RM2026** 的开源实现做互操作测试，共 3 个：JFCY2718（可运行模拟器）、ACE、ClearWei/RM26。
3. **双向通信全部成功**：
   - JFCY2718：第三方模拟器 → 本仓库 2027 客户端（7 类下行 **286 条**，0 未知/0 解码失败）；
     本仓库 2027 服务器 → 第三方 2026 proto 解码（**23/23**）；上行往返（SentryCtrlCommand ↔ SentryCtrlResult）**9 次**全部成功。
   - ACE：本仓库服务器 → 其 proto 解码 **23/23**（含 RadarInfoToClient）；其 proto 编码 **7 条** → 本仓库客户端解码 **7/7**。
   - ClearWei/RM26：其 **pb2** 编码 7 条 → 本仓库客户端 **7/7**；本仓库服务器 → 其 pb2 解码 **22/23**（`MapClickInfo` 缺失，见 §3.5）。
4. **Schema 对照**（32 条 2027 消息 vs 各实现）：
   | 实现 | 完全一致 | 仅字段名不同 | 2027 新增字段 | 线格式不兼容 | 我们缺失 |
   | :-- | --: | --: | --: | --: | :-- |
   | JFCY2718 | 28 | 2 | 2（含 Radar 留空） | **0** | — |
   | ACE | 28 | 3 | 1 | **0** | — |
   | ClearWei/RM26 | 26 | 3 | 1 | **0** | `MapClickInfo`、`MapClickCmd` |
5. **`RadarInfoToClient` 的分歧只存在于 JFCY2718**：它把官方原文声明留空；ACE 与 ClearWei 都按
   「嵌套 message + 字段 1」实现，与本仓库**线格式一致**，实测可互通。
6. 因此：**协议未修改的部分可以互通**；差异集中在 3 条消息的语义层（`GlobalUnitStatus`、
   `RobotDynamicStatus` 4、`RobotModuleStatus` 11）与各实现的版本滞后，与 [V1.0.0-变更分析.md](V1.0.0-变更分析.md) 的结论一致。

## 1. 调研：2027 有没有第三方实现？

### 1.1 结论

**没有。** 截止验证时（2026-10-29），RM2027 通信协议刚发布（V1.0.0，20261029），
公开仓库中不存在面向该版本的可用实现。

### 1.2 证据

- 发布日期差：GitHub 上相关仓库的最近更新均早于 2026-10-29（协议发布日）。
- 唯一标注「RM2027 自定义终端」的公开项目（[rgzrj/Custom_Client](https://github.com/rgzrj/Custom_Client)，Qt6/QML）在仓库规则中明确写：
  「官方通信协议未到位时，只实现明确标记的模拟接口与可替换适配层，不猜测主题名、字段、端口、服务质量或控制语义」，
  其模拟器的字段是**项目自造**，不能作为协议事实。
- GitHub 仓库搜索 `RoboMaster 2027` / `RM2027 custom client` / `robomaster 2027 protocol` 的结果中，
  除上述项目外均为算法/仿真/场地类仓库，无自定义终端协议实现。

### 1.3 找到的第三方自定义终端实现清单（均为上一赛季）

## 3. 测试结果

### 3.1 用例 A：JFCY 2026 模拟服务器 → 我们的 2027 客户端

```
node simulator/mqtt-simulator.mjs --port 18830 --robot 3 --team red --duration 20 &
build/rm_client --host 127.0.0.1 --port 18830 --client-id 3 --duration 10
```

| 指标 | 结果 |
| :-- | :-- |
| 订阅 | **23/23** 条下行全部订阅成功 |
| 收到的消息 | 7 类共 **286 条**：RobotPosition 99、RobotDynamicStatus 99、GameStatus 49、RobotStaticStatus 10、GlobalUnitStatus 10、GlobalLogisticsStatus 10、SentryStatusSync 9 |
| 未知指令 / 解码失败 | **0 / 0** |
| 未收到的 2026 消息 | `AirSupportStatusSync` —— 2027 已删除，客户端不再订阅（符合预期） |

解码样例（2027 结构体解 2026 数据）：

```json
{"topic":"GameStatus","data":{"currentRound":1,"totalRounds":3,"currentStage":4,
  "stageCountdownSec":418,"gameResult":255,"endReason":255,"isPaused":false,...}}
{"topic":"GlobalUnitStatus","data":{"robotHealth":[480,450,400,350,600,470,440,390,340,590],
  "outpostRHealth":700,"outpostBHealth":650,"totalCPAlly":0,"totalCPEnemy":0,...}}
{"topic":"RobotDynamicStatus","data":{"currentHealth":480,"reserved":80,...}}
```

注意：第三方发的是 10 个 `robot_health`、`outpost_health`/`enemy_outpost_health`、`current_chassis_energy`，
我们的 2027 结构体按同字段号接收后显示为 `robotHealth`（10 个）、`outpostRHealth`/`outpostBHealth`、`reserved` —— 
**线格式兼容、语义按 2027 解读**，这正是下文要提醒的风险。

### 3.2 用例 B：我们的 2027 服务器 → JFCY 2026 proto 解码

```
build/rm_server --host 127.0.0.1 --port 18841 --scenario tests/scenarios/all_down.json --interval 120 --start-after 1 --linger 4000 &
node peer_sub.mjs 18841 14000     # 用 JFCY 的 official-v2 proto 订阅并解码
```

| 指标 | 结果 |
| :-- | :-- |
| 解码成功 | **23/23** 条下行消息 |
| 解码失败 / 未知 topic | **0 / 0** |
| 新增字段可见性 | 我们的 `total_CP_ally/enemy`（15/16）在其 2026 proto 中不存在 → 作为未知字段丢弃（正常前向兼容） |
| 重命名映射 | `outpost_R_health`(4)→`outpost_health`(4)、`outpost_B_health`(9)→`enemy_outpost_health`(9) 等，值一致 |
| 语义错位示例 | 我们 `RobotDynamicStatus.reserved`=4900 → 对方解成 `current_chassis_energy`=4900；我们 `RobotModuleStatus.modular_42mm`=12000 → 对方解成 `laser_detection_module`=12000（值域 0/1 vs 0/1/2） |
| RadarInfoToClient | 对方**留空 message**（官方原文未给出完整声明，未实现），我们发出的字段被忽略 → 该话题在 JFCY 侧不可用 |

### 3.3 用例 C：上行 + 回包往返（JFCY）

```
node simulator/mqtt-simulator.mjs --port 18850 --ack success &
build/rm_client --port 18850 --client-id 3 --duration 5 --publish-scenario uplink_scenario.json
```

| 指标 | 结果 |
| :-- | :-- |
| 第三方解出我们的上行 | `COMMAND {"command_id":7}` × 9 次（按官方表 2-1 的 10Hz 触发） |
| 我们收到回包 | `SentryCtrlResult {"commandId":7,"resultCode":0}` × 9 次 |

`SentryCtrlCommand` / `SentryCtrlResult` 在 2026 V2.0.0 与 2027 V1.0.0 中字段完全一致，属于「未修改部分」。

### 3.5 用例 F/G：ClearWei/RM26_Client

ClearWei 的模拟器要求 Python ≥3.11 + FastAPI + OpenCV，本机为 Python 3.10，故改用其**生成的 `robomaster_pb2`**
（protobuf 6.33.2 运行时）作为对端；其 proto 共 51 条消息（含私有扩展如 `BattleMessage`、`MapMarking`）。

**F：其 pb2 编码 → 本仓库 2027 客户端解码**

| 指标 | 结果 |
| :-- | :-- |
| 解码成功 | **7/7** 条（GameStatus、GlobalUnitStatus、RadarInfoToClient、RobotDynamicStatus、RobotModuleStatus、PenaltyInfo、Buff） |
| 值对照 | 与 ACE 一致：`outpost_health`→`outpostRHealth`、`current_chassis_energy`→`reserved`、`laser_detection_module`→`modular_42mm`；`Buff`、`PenaltyInfo` 逐字段一致 |

**G：本仓库服务器 → 其 pb2 解码**

| 指标 | 结果 |
| :-- | :-- |
| 解码成功 | **22/23** 条 |
| 未能解码 | `MapClickInfo` 被跳过：其 proto 仍保留 v1.3.x 的 `MapClickInfoNotify`，**未跟进 2026 V2.0.0 的拆分**（`MapClickInfo` + `MapClickCmd`）；`MapClickCmd` 同样缺失 |
| 其余 | `RadarInfoToClient`、`GlobalUnitStatus`、`RobotDynamicStatus` 等 22 条均正常解码 |

> 这说明「上一赛季实现」也有版本差：ACE 是 V2.0.0，ClearWei 停留在 V1.3.x 的消息划分；
> 跨实现互通时除了 2026↔2027 的差异，还要考虑**对端自身的版本滞后**。

## 4. Schema 对照（本仓库 2027 vs 三个 2026 实现）

用 protobufjs 同时加载各方 `.proto`，按**字段号**逐条比对（本仓库 32 条）：

| 分类 | JFCY2718 | ACE | ClearWei/RM26 |
| :-- | --: | --: | --: |
| A. 字段号/类型/名字完全一致 | **28** | **28** | **26** |
| B. 仅字段名不同（线格式一致） | 2 | 3 | 3 |
| C. 2026 基线 + 2027 新增字段 | 2（含 Radar 留空） | 1 | 1 |
| D. 字段号/类型不兼容 | **0** | **0** | **0** |
| 我们缺失（对方没有的消息） | — | — | `MapClickInfo`、`MapClickCmd` |
| 对方独有 | 4（2027 删除项） | 5（4 删除 + `RadarSingleRobotInfo`） | 21（私有扩展 + 老消息） |

**A 类（三方共同，可直接互通）**：
`KeyboardMouseControl`、`CustomControl`、`GameStatus`、`GlobalLogisticsStatus`、`GlobalSpecialMechanism`、`Event`、
`RobotInjuryStat`、`RobotRespawnStatus`、`RobotStaticStatus`、`RobotPosition`、`Buff`、`PenaltyInfo`、`RobotPathPlanInfo`、
`MapClickInfo`/`MapClickCmd`（JFCY、ACE）、`CustomByteBlock`、`AssemblyCommand`、`TechCoreMotionStateSync`、
`RobotPerformanceSelectionCommand`、`RobotPerformanceSelectionSync`、`CommonCommand`、`RuneActivateCommand`、
`RuneStatusSync`、`SentryStatusSync`、`DartCommand`、`DartSelectTargetStatusSync`、`SentryCtrlCommand`、`SentryCtrlResult`。

**B 类（能解码但语义不同）**：

| 消息 | 2026 语义 | 2027 语义 | 风险 |
| :-- | :-- | :-- | :-- |
| `GlobalUnitStatus` 4/5/9/10 | 己方/对方前哨站（相对口径） | R/B 前哨站（固定场地口径） | 蓝方角色会读反；`robot_health` 由 10 个变 8 个 |
| `GlobalUnitStatus` 15/16 | 不存在 | 己方/对方累计控制度 | 旧端看不到（前向兼容，正常） |
| `RobotDynamicStatus` 4 | 当前剩余底盘能量 | 保留位 `reserved` | 旧值会被误当能量 |
| `RobotModuleStatus` 11 | 激光检测模块状态（0/1/2） | 模块化 42mm 安装权限（0/1，仅重装） | 旧端可能发出 2，越出 2027 值域 |
| `RadarInfoToClient` | 嵌套 message（ACE/ClearWei）或留空（JFCY） | 嵌套 message，每方 4 台、共 8 元素 | 线格式 ACE/ClearWei 可通；但**元素个数/顺序** 2027 已变（6→4 台），数值含义需按版本换算 |

**关于 `RadarInfoToClient` 的结论修正**：
- JFCY2718 选择「留空、不订阅」→ 与其不可互通；
- ACE（`robots_info`）与 ClearWei（`robot_info`）都实现为「嵌套 message + 字段 1」，与本仓库**线格式完全一致**，
  实测双向可解码。
- 因此该话题的互通性取决于对端是否实现了该声明，而不是协议本身不可实现；2027 的元素个数（8 个、顺序 1/3/4/7）
  仍需按版本换算。

## 5. 结论

1. **协议正确性得到 3 份独立实现验证**：28/28/26 条消息在字段号与类型上完全对齐，三份实现均**无一条线格式不兼容**，
   双向收发无解码失败。
2. **未修改的部分可以互通**：A 类消息在 2026↔2027 之间可直接通信（用例 A–G 已实证）。
3. **修改的部分能解码、不能直接采信**：`GlobalUnitStatus`、`RobotDynamicStatus` 4、`RobotModuleStatus` 11 需按协议版本做语义映射
   （`robot_health` 长度、`base_shield` 语义、`reserved`、`modular_42mm` 值域）。
4. **上一赛季实现之间也有版本差**：ClearWei 停留在 v1.3.x 的 `MapClickInfoNotify` 划分，缺少 `MapClickInfo`/`MapClickCmd`；
   跨实现联调时需同时确认对端协议版本。
5. **`RadarInfoToClient` 已有两份实现与本仓库线格式一致**（ACE、ClearWei），JFCY 的留空属其自身选择；
   该话题的最终定稿仍建议以真实裁判系统实测为准。

## 6. 局限

- 三份对端都是 **上一赛季（2026）** 实现；2027 的第三方实现尚不存在（协议 2026-10-29 才发布）。
- ACE 与 ClearWei 的完整 GUI 程序未运行（依赖 Qt6/ImGui/预编译 FFmpeg 或 Python≥3.11+FastAPI），
  只验证了**协议定义/生成代码**层面的线格式与字段语义，未验证其业务逻辑。
- 未验证图传（UDP 3334）跨实现互通；两版封帧规则逐字相同，本仓库已有独立压力测试覆盖。
- 未在真实裁判系统/官方客户端上验证；语义差异只能靠版本分支处理，互通测试无法证明语义正确。

## 7. 复现方式

第三方材料**不入库**，复现时在仓库外准备（示例路径 `.scratch-interop/`）：

```bash
export https_proxy=http://127.0.0.1:7897 http_proxy=http://127.0.0.1:7897 all_proxy=socks5://127.0.0.1:7897
mkdir -p .scratch-interop && cd .scratch-interop
git clone --depth 1 https://github.com/JFCY2718/rmuc-custom-client-ui.git
git clone --depth 1 https://github.com/ACE-Algorithm/ACE_RM26_CustomClient.git
git clone --depth 1 https://github.com/ClearWei/RM26_Client.git

# Node 端（Aedes + protobufjs + mqtt）
cd rmuc-custom-client-ui/simulator && npm install --no-audit --no-fund aedes mqtt protobufjs && cd ../..

# Python 端（ClearWei 的 pb2 需要 protobuf 6.33.2）
python3 -m venv venv && ./venv/bin/pip install paho-mqtt protobuf==6.33.2

# 用例 A
node rmuc-custom-client-ui/simulator/mqtt-simulator.mjs --port 18830 --robot 3 --team red --duration 20 &
RM2027-CustomTerminal-CommunicationBackend/build/rm_client --port 18830 --client-id 3 --duration 10

# 用例 B/D/G：启动本仓库服务器发布场景，再用对方 proto/pb2 订阅解码
RM2027-CustomTerminal-CommunicationBackend/build/rm_server --port 18841 \
  --scenario RM2027-CustomTerminal-CommunicationBackend/tests/scenarios/all_down.json --start-after 1 &
node <对方 proto 解码脚本> 18841 12000          # ACE / JFCY
./venv/bin/python peer_rm26_sub.py 18841 12000   # ClearWei pb2

# 用例 E/F：本仓库 broker + 客户端，对方编码后发布
RM2027-CustomTerminal-CommunicationBackend/build/rm_server --port 18861 &
RM2027-CustomTerminal-CommunicationBackend/build/rm_client --port 18861 --duration 7 &
node <对方 proto 编码脚本> 18861                 # ACE
./venv/bin/python peer_rm26_pub.py 18861         # ClearWei pb2
```

对端脚本都是 30 行左右的小脚手架：用对方的 proto / pb2 建立编解码器，连到 `rm_server`/`rm_client` 的
MQTT 端口收发；核心只有两句：

```js
const type = root.lookupType(topic);                                    // Node（protobufjs）
console.log(type.toObject(type.decode(payload), {longs:String, defaults:true}));
```

```python
msg = getattr(pb, topic)(); msg.ParseFromString(payload)                # Python（ClearWei pb2）
```
