# 互操作验证：与第三方开源自定义终端实现对照

**目的**：用**独立实现**验证本仓库的通信协议实现是否正确（编解码、字段编号、线格式），
并确认 RM2027 与上一赛季协议中**未修改的部分**能否跨实现互通。

**结论摘要**

1. **没有可用的 RM2027 第三方开源实现**：2027 协议 V1.0.0 于 2026-10-29 才发布，公开仓库均早于该日期；
   唯一标注 RM2027 的项目明确声明「官方协议未到位时不猜测字段」，只做模拟接口。
2. 改用 **RM2026 V2.0.0** 的开源实现（JFCY2718/rmuc-custom-client-ui）做互操作测试。
3. **双向通信全部成功**：第三方模拟器 → 本仓库 2027 客户端（7 类下行 286 条，0 未知/0 解码失败）；
   本仓库 2027 服务器 → 第三方 2026 proto 解码（23/23 条，0 失败）；上行往返（SentryCtrlCommand ↔ SentryCtrlResult）9 次全部成功。
4. **Schema 对照**：32 条 2027 消息中 **28 条字段号/类型/名字完全一致**、2 条仅字段名变（线格式一致）、
   1 条为 2026 基线 + 2 个新增字段；**0 条线格式不兼容**；`RadarInfoToClient` 因官方文档残缺而实现分歧（第三方留空）。
5. 因此：**协议未修改的部分可以互通**；差异集中在 3 条消息的语义层与 1 条文档歧义，与 [V1.0.0-变更分析.md](V1.0.0-变更分析.md) 的结论一致。

## 1. 调研：2027 有没有第三方实现？

### 1.1 结论

**没有。** 截止验证时（2026-10-29），RM2027 通信协议刚发布（V1.0.0，20261029），
公开仓库中不存在面向该版本的可用实现。

### 1.2 证据

- 发布日期差：GitHub 上相关仓库的最近更新均早于 2026-10-29（协议发布日）。
- 唯一标注「RM2027 自定义终端」的公开项目（`rgzrj/Custom_Client`，Qt6/QML）在仓库规则中明确写：
  「官方通信协议未到位时，只实现明确标记的模拟接口与可替换适配层，不猜测主题名、字段、端口、服务质量或控制语义」，
  其模拟器的字段是**项目自造**，不能作为协议事实。
- GitHub 仓库搜索 `RoboMaster 2027` / `RM2027 custom client` / `robomaster 2027 protocol` 的结果中，
  除上述项目外均为算法/仿真/场地类仓库，无自定义终端协议实现。

### 1.3 找到的第三方自定义终端实现清单（均为上一赛季）

| 仓库 | 语言 | 协议版本 | 说明 |

## 3. 测试结果

### 3.1 用例 A：第三方 2026 模拟服务器 → 我们的 2027 客户端

```
node simulator/mqtt-simulator.mjs --port 18830 --robot 3 --team red --duration 20 &
build/rm_client --host 127.0.0.1 --port 18830 --client-id 3 --duration 10
```

结果（`rm_client` 的 stderr / stdout 记录）：

```
INFO client 已连接 broker
INFO client 订阅完成: 23/23 条下行指令
INFO client ↓ RobotStaticStatus / GlobalUnitStatus / GlobalLogisticsStatus / RobotDynamicStatus / RobotPosition / GameStatus / SentryStatusSync
```

| 指标 | 结果 |
| :-- | :-- |
| 订阅 | **23/23** 条下行全部订阅成功（第三方 Aedes broker） |
| 收到的消息 | 7 类共 **286 条**：RobotPosition 99、RobotDynamicStatus 99、GameStatus 49、RobotStaticStatus 10、GlobalUnitStatus 10、GlobalLogisticsStatus 10、SentryStatusSync 9 |
| 未知指令 / 解码失败 | **0 / 0** |
| 未收到的 2026 消息 | `AirSupportStatusSync` —— 2027 已删除，客户端不再订阅（符合预期） |

解码样例（我们的 2027 客户端解第三方 2026 数据）：

```json
{"topic":"GameStatus","data":{"currentRound":1,"totalRounds":3,"currentStage":4,
  "stageCountdownSec":418,"gameResult":255,"endReason":255,"isPaused":false,...}}
{"topic":"GlobalUnitStatus","data":{"robotHealth":[480,450,400,350,600,470,440,390,340,590],
  "outpostRHealth":700,"outpostBHealth":650,"totalCPAlly":0,"totalCPEnemy":0,...}}
{"topic":"RobotDynamicStatus","data":{"currentHealth":480,"reserved":80,...}}
```

注意：第三方发的是 10 个 `robot_health`、`outpost_health`/`enemy_outpost_health`、`current_chassis_energy`，
我们的 2027 结构体按同字段号接收后显示为 `robotHealth`（10 个）、`outpostRHealth`/`outpostBHealth`、`reserved` —— 
**线格式兼容、语义按 2027 解读**，这正是下一节要提醒的风险。

### 3.2 用例 B：我们的 2027 服务器 → 第三方 2026 proto 解码

```
build/rm_server --host 127.0.0.1 --port 18841 --scenario tests/scenarios/all_down.json --interval 120 --start-after 1 --linger 4000 &
node peer_sub.mjs 18841 14000     # 用第三方的 official-v2 proto 订阅并解码
```

| 指标 | 结果 |
| :-- | :-- |
| 解码成功 | **23/23** 条下行消息（第三方 proto 全部认识） |
| 解码失败 / 未知 topic | **0 / 0** |
| 新增字段可见性 | 我们的 `total_CP_ally/enemy`（15/16）在 2026 proto 中不存在 → 被当作未知字段丢弃（正常的前向兼容） |
| 重命名映射 | `outpost_R_health`(4)→第三方 `outpost_health`(4)、`outpost_B_health`(9)→`enemy_outpost_health`(9) 等，值一致 |
| 语义错位示例 | 我们 `RobotDynamicStatus.reserved`=4900 → 第三方解成 `current_chassis_energy`=4900；我们 `RobotModuleStatus.modular_42mm`=12000 → 第三方解成 `laser_detection_module`=12000（值域 0/1 vs 0/1/2） |

第三方解码样例（其 proto 字段名）：

```json
DECODED GameStatus {"current_round":1100,"total_rounds":2100,"red_score":3100,
  "blue_score":4100,"current_stage":5100,...,"game_result":9100,"end_reason":10100}
DECODED GlobalUnitStatus {"robot_health":[11200,11200],"base_health":1200,
  "outpost_health":4200,"enemy_outpost_health":9200,...,"total_damage_ally":13200}
DECODED RobotDynamicStatus {"current_health":1900,...,"current_chassis_energy":4900,...}
```

### 3.3 用例 C：上行 + 回包往返

第三方模拟器会在收到 `SentryCtrlCommand` 后回 `SentryCtrlResult`（2026 proto 中该消息与 2027 完全一致）：

```
node simulator/mqtt-simulator.mjs --port 18850 --ack success &
build/rm_client --port 18850 --client-id 3 --duration 5 --publish-scenario uplink_scenario.json
```

| 指标 | 结果 |
| :-- | :-- |
| 第三方解出我们的上行 | `COMMAND {"command_id":7}` × 9 次（我们按官方表 2-1 的 10Hz 触发） |
| 我们收到回包 | `SentryCtrlResult {"commandId":7,"resultCode":0}` × 9 次 |

说明：`SentryCtrlCommand` / `SentryCtrlResult` 在 2026 V2.0.0 与 2027 V1.0.0 中字段完全一致，属于「未修改部分」。

## 4. Schema 对照（本仓库 2027 vs 第三方 2026 V2.0.0）

用 protobufjs 同时加载两边的 `.proto`，按**字段号**逐条比对（第三方 36 条 vs 本仓库 32 条）：

| 分类 | 数量 | 说明 |
| :-- | --: | :-- |
| A. 字段号/类型/名字完全一致 | **28** | 可直接互通 |
| B. 仅字段名不同（线格式一致） | **2** | `RobotDynamicStatus` 4、`RobotModuleStatus` 11 |
| C. 2026 基线 + 2027 新增字段 | **1** | `GlobalUnitStatus`（4/5/9/10 改名 + 15/16 新增） |
| D. 字段号/类型不兼容 | **0** | — |
| E. 第三方未实现（官方文档残缺） | **1** | `RadarInfoToClient`（第三方留空 message） |
| 仅 2026 有（2027 删除） | **4** | `HeroDeployModeEventCommand`、`DeployModeStatusSync`、`AirSupportCommand`、`AirSupportStatusSync` |

**A 类（28 条，可直接互通）**：
`KeyboardMouseControl`、`CustomControl`、`GameStatus`、`GlobalLogisticsStatus`、`GlobalSpecialMechanism`、`Event`、
`RobotInjuryStat`、`RobotRespawnStatus`、`RobotStaticStatus`、`RobotPosition`、`Buff`、`PenaltyInfo`、`RobotPathPlanInfo`、
`MapClickInfo`、`MapClickCmd`、`CustomByteBlock`、`AssemblyCommand`、`TechCoreMotionStateSync`、
`RobotPerformanceSelectionCommand`、`RobotPerformanceSelectionSync`、`CommonCommand`、`RuneActivateCommand`、
`RuneStatusSync`、`SentryStatusSync`、`DartCommand`、`DartSelectTargetStatusSync`、`SentryCtrlCommand`、`SentryCtrlResult`。

**B/C 类（3 条，能解码但语义不同）**：

| 消息 | 2026 语义 | 2027 语义 | 风险 |
| :-- | :-- | :-- | :-- |
| `GlobalUnitStatus` 4/5/9/10 | 己方/对方前哨站（相对口径） | R/B 前哨站（固定场地口径） | 蓝方角色会读反；`robot_health` 由 10 个变 8 个 |
| `GlobalUnitStatus` 15/16 | 不存在 | 己方/对方累计控制度 | 旧端看不到（前向兼容，正常） |
| `RobotDynamicStatus` 4 | 当前剩余底盘能量 | 保留位 `reserved` | 旧值会被误当能量 |
| `RobotModuleStatus` 11 | 激光检测模块状态（0/1/2） | 模块化 42mm 安装权限（0/1，仅重装） | 旧端可能发出 2，越出 2027 值域 |

**E 类（1 条，不可互通）**：`RadarInfoToClient`。官方 PDF 该节声明不完整、类型写错
（原文 `repeated uint32 RadarSingleRobotInfo;`），本仓库按「嵌套 message」实现，
第三方实现选择「留空、不订阅，等待实测证据」。**这是官方文档歧义导致的实现分歧，不是本仓库的缺陷**，
但跨实现联调时该话题必然对不上，需要以真实裁判系统实测为准。

## 5. 结论

1. **协议正确性得到独立实现验证**：我们的 2027 编解码与一份独立转写的 2026 协议实现在 28 条消息上完全对齐，
   双向收发无解码失败。
2. **未修改的部分可以互通**：28 条 A 类消息在 2026↔2027 之间可直接通信（用例 A/B/C 已实证）。
3. **修改的部分能解码、不能直接采信**：B/C 类 3 条消息需按协议版本做语义映射（尤其是 `robot_health` 长度、
   `base_shield` 语义、`reserved`、`modular_42mm` 值域）。
4. **2026 端不需要理解 2027 的新增/删除**：新增字段被旧端忽略（正常），删除的 4 条旧端收不到也不影响。
5. **唯一硬分歧**：`RadarInfoToClient`，源于官方文档残缺；建议在拿到真实裁判系统数据后再定稿。

## 6. 局限

- 只核对了 **一个** 第三方实现（2026 V2.0.0）。2026 V1.3.x 及更早版本的实现与 2027 的字段差异更大，未逐一验证。
- 未验证图传（UDP 3334）跨实现互通；但两版封帧规则逐字相同，本仓库已有独立压力测试覆盖。
- 未在真实裁判系统/官方客户端上验证；本测试验证的是「第三方协议实现」，不是官方实现。
- 语义差异（如 `robot_health` 长度、基地阵地控制状态）只能靠版本分支处理，互通测试无法证明语义正确。

## 7. 复现方式

第三方材料**不入库**，复现时按以下步骤在仓库外准备（示例路径 `.scratch-interop/`）：

```bash
export https_proxy=http://127.0.0.1:7897 http_proxy=http://127.0.0.1:7897 all_proxy=socks5://127.0.0.1:7897
mkdir -p .scratch-interop && cd .scratch-interop
git clone --depth 1 https://github.com/JFCY2718/rmuc-custom-client-ui.git
cd rmuc-custom-client-ui/simulator
npm install --no-audit --no-fund aedes mqtt protobufjs

# 用例 A
node mqtt-simulator.mjs --port 18830 --robot 3 --team red --duration 20 &
../../../RM2027-CustomTerminal-CommunicationBackend/build/rm_client --host 127.0.0.1 --port 18830 --client-id 3 --duration 10

# 用例 B：用第三方 proto 做订阅端（脚本见下）
node peer_sub.mjs 18841 14000 &
../../../RM2027-CustomTerminal-CommunicationBackend/build/rm_server --port 18841 \
  --scenario ../../../RM2027-CustomTerminal-CommunicationBackend/tests/scenarios/all_down.json --start-after 1

# 用例 C
node mqtt-simulator.mjs --port 18850 --ack success &
../../../RM2027-CustomTerminal-CommunicationBackend/build/rm_client --port 18850 --client-id 3 \
  --duration 5 --publish-scenario uplink_scenario.json
```

其中 `uplink_scenario.json` 内容：`{"steps":[{"topic":"SentryCtrlCommand","data":{"command_id":7}}]}`；
`peer_sub.mjs` 是一个约 30 行的 Node 脚本：用第三方的 `official-v2` proto（`keepCase: true`）建 protobuf root，
连到 `rm_server` 后订阅 `#`，按 topic 名查消息类型并 `decode`，打印字段。核心片段：

```js
import mqtt from "mqtt";
import protobuf from "protobufjs";
const root = protobuf.parse(readFileSync(".../official-v2/rmuc_official_v2.proto","utf8"), {keepCase:true}).root;
// 收到消息后：
const type = root.lookupType("rmuc.official_v2." + topic);
console.log(type.toObject(type.decode(payload), {longs:String, defaults:true}));
```
