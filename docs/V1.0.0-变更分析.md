## 0. 结论速览

| 维度 | 结论 |
| :-- | :-- |
| 章节名称 | 「自定义**客户端**协议」→「自定义**终端**协议」（概念合并，不只是改名） |
| 指令数量 | **36 条 → 32 条**：整节删除 4 条，**无任何新增**（上行 11→9、下行 25→23） |
| 传输层 | MQTT `192.168.12.1:3333`、UDP 图传 `3334`、Protobuf v3（≥ 3.15）、`qos=1` **全部不变** |
| 发送频率 / 方向 / qos | **方向 / qos**：32 条保留指令逐行一致；**频率**：29/32 逐值一致，`MapClickInfo` / `MapClickCmd` 的 1.3.1 附加频率限制与 `Buff` 的触发式语义未建模（见 README） |
| 字节上限 | 唯一变化：`CustomControl` **30 → 60 字节**（对应图传 `0x0311` 载荷 30→60） |
| 破坏性变化 | 集中在 `GlobalUnitStatus` / `GameStatus` / `Event` / `GlobalSpecialMechanism` / `RadarInfoToClient` / `RobotModuleStatus`（另 `RobotDynamicStatus`、`RobotStaticStatus` 有语义收窄） |
| 术语 | 英雄/工程 → **重装**；空中机器人 → **空中系统**；云台手 → **指挥手**；发射机构 → **测速模块**；飞坡 → **高地**；前哨站 → **R 前哨 / B 前哨** |
| 兼容性 | 线格式多处不兼容，**必须按版本分支或整体升级** |

**最需要警惕的 5 处（按踩坑概率排序）**

1. `GlobalUnitStatus` 字段 3/8 的 proto 名仍是 `base_shield` / `enemy_base_shield`，但语义已从「基地护盾值」
   变成「基地**阵地控制状态**」——照 proto 名实现必然误判。
2. `GlobalUnitStatus.robot_health` 元素个数 **10 → 8**（每方由 `1,2,3,4,7` 改为 `1,3,4,7`）。
3. `GameStatus.end_reason` **9 项 → 7 项并整体重编号**，同一数值含义全变（2 号由「基地剩余血量」变为「控制度」）。
4. `Event.event_id` 大量**编号复用**：5/6（狙击伤害 → R/B 前哨阵地控制状态）、7/8（空中支援 → R/B 基地阵地控制方）。
5. 4 条指令**整节删除**：英雄部署模式 2 条、空中支援 2 条，功能未被任何现存指令吸收。

## 1. 变化根因：2027 规则层重构

2027 通信协议 V1.0.0 的修改日志只有一行「首次发布」，未说明改动来源。变化动因可从
《RoboMaster 2027 高校系列赛规则变更前瞻手册（20260909）》第 1 章「新赛季主要变更概述」逐条对应：

> - 「**原英雄机器人和工程机器人合并为重装机器人。**」
> - 「**原自定义控制器与自定义客户端合并为自定义终端。**」
> - 「**重构空中机器人的部署方式、使用方式及功能。**」

这三条几乎线性解释了本协议章节的全部结构性变化：

* 英雄（ID 1）与工程（ID 2）合并 → ID 1 变为「重装机器人」、ID 2 变为「保留位」，
  `RobotStaticStatus` 里英雄专属的性能体系枚举项被删；
* 自定义控制器并入自定义终端 → 章名 / 附录名改名，`0x0302` / `0x0306` / `0x0309` 三条
  自定义控制器命令码从第 1 章消失；
* 空中机器人重构 → 称谓改「空中系统」，空中支援（`AirSupport*`）与英雄部署模式（`*DeployMode*`）
  协议整体删除。

## 3. 指令级变化：36 → 32（删 4 条，无新增）

### 3.1 删掉的 4 条

| 指令 | 2026 小节 | 方向 / 频率 | 定义 | 删除后功能去向 |
| :-- | :-- | :-- | :-- | :-- |
| `HeroDeployModeEventCommand` | 2.2.26 | 上行，触发式 ≤10Hz | `mode`（0=退出，1=进入） | **无替代**（英雄已并入重装） |
| `DeployModeStatusSync` | 2.2.27 | 下行，1Hz | `status`（0=未部署，1=已部署） | **无替代** |
| `AirSupportCommand` | 2.2.35 | 上行，触发式 | `command_id`：0 取消 / 1 免费呼叫 / 2 花金币呼叫 / 3 花金币解除反制 | **无替代**（空中系统机制重构） |
| `AirSupportStatusSync` | 2.2.36 | 下行，1Hz | 5 字段：支援状态、免费剩余时间、已花金币、是否被激光照射、发射机构被反制状态（含 `airsupport_status` / `shooter_status` 两枚举） | **无替代** |

**判定依据**：消息总数 36→32 且 2027 **无新增消息**；`CommonCommand.cmd_type` 仍严格为 1–6 未增一项；
`SentryCtrlCommand` 指令编号仍跳号 2（1,3–12）未增；2027 全 PDF 中「空中支援 / AirSupport / DeployMode /
部署模式 / 反制 / 激光 / 狙击」命中均为 **0**。**结论：功能被规则层取消，而不是换了通道下发。**

### 3.2 2.1 概览表其余变化（28 条保留指令里只有 4 处）

| 指令 | RM2026 | RM2027 | 类型 |
| :-- | :-- | :-- | :-- |
| `CustomControl` | 最大 **30 字节**的自定义数据 | 最大 **60 字节**的自定义数据 | 上限 |
| `GlobalUnitStatus` | 同步基地、前哨站和所有机器人状态 | 同步**全局胜负相关**状态 | 用途 |
| `AssemblyCommand` | **工程**装配指令 | **重装**装配指令 | 用途 |
| `RobotPerformanceSelectionSync` | 步兵/**英雄**性能体系状态同步 | 步兵/**重装**性能体系状态同步 | 用途 |

> ⚠️ 2027 文档自身不一致：概览表写「步兵/**重装**性能体系状态同步」，但正文 2.2.24 写「**步兵**性能体系状态同步」。
> 结合前瞻手册「重装机器人关键特征：经验与性能体系不适用」，正文更可信；本项目按正文语义处理，字段与 proto 不变。

**其余 28 条的方向、qos 逐行一致**；发送频率为 **29/32 逐值一致**——`MapClickInfo` / `MapClickCmd` 的 1.3.1 附加频率限制与 `Buff` 的触发式语义未建模，已在 README 说明。

## 4. 字段级变化（逐条）

### 4.1 `CustomControl`（2.2.2）—— 唯一字节上限变化

| 项目 | RM2026 | RM2027 |
| :-- | :-- | :-- |
| 用途 | 最大 **30 字节**的自定义数据 | 最大 **60 字节**的自定义数据 |
| 字段 1 | `bytes` 最大 30 字节 | `bytes` 最大 60 字节 |
| 承载 | 图传 `0x0311`（30 字节） | 图传 `0x0311`（**60 字节**） |

proto 本身无需改（`bytes` 类型不变），但**发送缓冲、分片与对端解析长度必须同步扩容**。

### 4.2 `GlobalUnitStatus`（2.2.4）—— 全章变化最大

| 字段 | RM2026 | RM2027 | proto 名 |
| --: | :-- | :-- | :-- |
| 用途 | 同步基地、前哨站和所有机器人状态 | 同步**全局胜负相关**状态 | — |
| 3 | 己方基地**当前护盾值**（0=无护盾） | 己方基地**阵地控制状态**（1 被己方完全控制 / 2 被对方临时控制） | `base_shield` **未改** |
| 4 | 己方前哨站当前血量 | **R 前哨站**当前血量 | `outpost_health` → `outpost_R_health` |
| 5 | 己方前哨站状态（枚举 0–5） | **R 前哨阵地**控制状态（1 己方完全 / 2 己方临时 / 3 对方临时 / 4 对方完全） | `outpost_status` → `outpost_R_status` |
| 8 | 对方基地**当前护盾值** | 对方基地**阵地控制状态**（1 被对方完全控制 / 2 被己方临时控制） | `enemy_base_shield` **未改** |
| 9 | 对方前哨站当前血量 | **B 前哨站**当前血量 | `enemy_outpost_health` → `outpost_B_health` |
| 10 | 对方前哨站状态 | **B 前哨阵地**控制状态（同字段 5 的 4 档） | `enemy_outpost_status` → `outpost_B_status` |
| 11 | `robot_health` 顺序：己方 `1,2,3,4,7` + 对方 `1,2,3,4,7` = **10 个** | 己方 `1,3,4,7` + 对方 `1,3,4,7` = **8 个** | 类型不变，**长度约定变** |
| 15/16 | — | **新增**：己方 / 对方累计控制度 | `total_CP_ally` / `total_CP_enemy` |
| `base_status` 枚举 | 0 无敌 / 1 解除无敌护甲未展开 / 2 解除无敌护甲展开 | 0 **拥有 100% 防御增益** / 1 不拥有…未展开 / 2 不拥有…展开 | 档位不变，措辞变 |
| `outpost_status` 枚举 | **存在**：0 无敌 / 1 存活装甲旋转 / 2 存活装甲停转 / 3 击毁不可重建 / 4 击毁可重建 / 5 击毁重建中 | **整块删除** | 语义被字段 5/10 的「阵地控制 4 档」取代 |

**两个口径陷阱**

* **R/B 前哨站是按场地位置固定的绝对口径**（R=开局红方一侧），而字段 1/2/6/7 的基地仍用「己方/对方」相对口径
  —— 形成「基地相对、前哨站绝对」的不对称。**蓝方终端读字段 4 拿到的将是对方前哨站血量，与 2026 行为相反。**
* 基地阵地控制只有 **2 档**，前哨阵地有 **4 档**，不要混用同一套判定。

### 4.3 `GameStatus`（2.2.3）—— 只有 `end_reason` 变了

`current_stage` 6 项完全不变（0 未开始 / 1 准备 / 2 十五秒自检 / 3 五秒倒计时 / 4 比赛中 / 5 结算中），
字段 1–10 的类型与含义亦不变（`game_result` 9 仍在结算阶段有意义，其余时间发 255）。

| 值 | RM2026 的 `end_reason` | RM2027 的 `end_reason` |
| --: | :-- | :-- |
| 1 | 基地被摧毁 | 基地被摧毁 |
| 2 | 基地剩余血量 | **控制度** ← 新增语义 |
| 3 | 前哨站剩余血量 | 全队总攻击伤害（原 5） |
| 4 | 前哨站是否被击毁过 | 全队机器人总剩余血量（原 6） |
| 5 | 全队总攻击伤害 | 平局（原 7） |
| 6 | 全队机器人总剩余血量 | 异常终止（原 8） |
| 7 | 平局 | 主裁判手动判定胜负（原 9） |
| 8 | 异常终止 | — |
| 9 | 主裁判手动判定胜负 | — |

删除 2/3/4 三项前哨站相关原因，新增 1 项「控制度」，其余整体前移。**跨版本共用解析代码必须按协议版本分支。**

| event_id | RM2026 | RM2027 | 类型 |

| 5 | 己方英雄造成狙击伤害（累计值） | **R 前哨阵地改变控制状态**（1 红临时 / 2 红完全 / 3 蓝临时 / 4 蓝完全） | 复用 + 改义 |

| 7 | 对方呼叫空中支援（无参数） | **R 基地阵地改变控制方**（1 红完全 / 2 蓝临时） | 删除 + 复用 |
| 8 | 对方空中支援被反制（剩余次数） | **B 基地阵地改变控制方**（1 蓝完全 / 2 红临时） | 删除 + 复用 |

| 15 | 装配结果事件（… 4 工程战亡 …） | 同结构，参数 4 改「**重装**战亡」 | 措辞 |

基地阵地类事件只有 **2 档**参数，前哨阵地类有 **4 档**，与 4.2 的字段档位一一对应。

### 4.5 `GlobalSpecialMechanism`（2.2.6）—— 2 项 → 6 项，时间参数新增符号语义

| 项 | RM2026 | RM2027 |
| --: | :-- | :-- |
| 1 | 己方堡垒被对方**占领**计时 | 己方堡垒被对方**激活**计时 |
| 2 | 对方堡垒被己方占领计时 | 对方堡垒被己方激活计时 |
| 3 | — | **R 前哨阵地激活计时** |
| 4 | — | **B 前哨阵地激活计时** |
| 5 | — | **R 基地阵地激活计时** |
| 6 | — | **B 基地阵地激活计时** |

新增规则原文：「**符号表示方向，＜0 为对方正在推进激活进度，＞0 为己方正在推进激活进度，0 为激活状态无变化。下同**」。
单位仍为秒，但**不能取绝对值**。

### 4.6 `RadarInfoToClient`（2.2.19）—— 每方 6 台 → 4 台

| 项目 | RM2026 | RM2027 |
| :-- | :-- | :-- |
| 每方机器人顺序 | 1 号, 2 号, 3 号, 4 号, **6 号**, 7 号（6 台） | 1 号, 3 号, 4 号, 7 号（**4 台**） |
| 单次触发结构数 | 12（6+6） | **8**（4+4） |
| `repeated uint32` 载荷 | 36 个 uint32（每结构 3 个） | **24 个**（默认嵌套实现为 8 个嵌套结构 × 3 字段；flat 模式才是 24 个 uint32） |

（5 号步兵两版都不在清单中，不是本次变化；2 号 / 6 号退出是因为 ID 2 变成保留位、6 号改为空中系统。）

**线格式存在「官方原文字面」与「嵌套 message」两种解释**：官方 §2.2.19 代码块字面写
`repeated uint32 RadarSingleRobotInfo;`（字段号未给出、字段名使用了结构体名，**该声明本身不是合法的 proto**）；
常见开源实现（ACE / ClearWei）采用嵌套 message，与官方字面不同。本项目**两种都实现、默认嵌套、可切换**：
默认 `NestedMessage`（嵌套 message，与 ACE / ClearWei 等第三方实现一致）；
可选 `FlatPackedUint32`（严格按官方字面：字段 1 packed repeated uint32，24 个 uint32）。
切换方式：C++ `rm2027::setRadarWireFormat()`；C `rm_set_radar_wire_format(0|1)`；
Python `rm.set_radar_wire_format("nested"|"flat")`；CLI `--radar-wire-format nested|flat`（`rm_server` / `rm_client`）。
JSON / 日志始终用嵌套形式。详见根目录 README「雷达线格式」。

## 6. 相邻章节：图传链路 `0x0311` 30 → 60 字节

| 命令码 | RM2026 | RM2027 |
| :-- | :-- | :-- |

「**1.4.1 自定义终端与机器人交互数据说明**」—— 这正是「自定义控制器 + 自定义客户端 = 自定义终端」
在协议结构上的落地。

附录三（C# `MyMqttClient` 示例）代码主体逐字一致；2026 版本末尾混入的一段
「`0x016A`：蓝方空中机器人选手端 / `ext_robot_command_t` / 机器人 ID 清单」在 2027 中被删除
（该段与附录主题无关，属 2026 的编排瑕疵）。

**UDP 图传封帧规则两版完全相同**（8 字节大端包头 / 单包 1400B、负载 1392B / HEVC / 无重传 / 60fps 1920×1080），

## 8. 与官方一致性（逐字段对齐 2027 PDF）

**结论**：本项目 **31/32 条协议消息**与官方 2027 V1.0.0 PDF §2.2 **字面一致**
（字段名、字段号、类型、`repeated` 标签、嵌套结构、proto3 `optional` 写法、`[packed]` 选项均一致）；
唯一偏离是 `RadarInfoToClient`——官方字面为 `repeated uint32 RadarSingleRobotInfo;`（字段号未给出），
本项目**有意**实现双线格式：默认嵌套 message，可用 flat packed 模式严格对应官方字面（见 §4.6 与 README）。
辅助 message `RadarSingleRobotInfo` 在本项目中为嵌套定义，字段字面一致。

**核对方式**：

```bash
# 1) 抽取官方 PDF 全文（保留版式）
pdftotext -layout -enc UTF-8 "../rule-documents/RoboMaster 2027 机甲大师高校系列赛通信协议 V1.0.0（20261029）.pdf" p2027.txt

# 2) 与项目 proto 逐字段机器**字面**比对（32 条协议消息；默认应得 31/32 + 1 条已知偏离并退出 0，--strict 则退出 1）
python3 tools/diff_protocol_versions.py p2027.txt proto
```

**官方原文写法与歧义的处理**（均已在 proto 或工具中注明）：

| # | 问题 | 本项目处置 |
| --: | :-- | :-- |
| 1 | `RadarInfoToClient` 原文 `repeated uint32 RadarSingleRobotInfo;`（字段号未给出、类型写作 uint32，**该声明本身不是合法的 proto**；常见开源实现采用嵌套 message，与其不同） | **双模式**：默认嵌套 message（`repeated RadarSingleRobotInfo radar_single_robot_info = 1;`）；另提供 flat packed 模式（`proto/rm2027_radar_flat.proto`：`repeated uint32 radar_single_robot_info = 1;`，补上字段号，24 个 uint32）严格对应官方字面。两者可切换，**默认嵌套**（默认值理由与实测见 README） |
| 2 | `MapClickInfo` / `MapClickCmd` 表格把「3=标记类型、6=标记模式」，proto 却是 `type=6`、`mode=3`（**两版同样错位**） | 以 proto 字段号为准（`type=6` / `mode=3`），字段名不变 |
| 3 | `Event` 14 / 16 号在 2027 未标注「（无参数）」 | 参数是否存在按 `string param` 透传，不做强校验 |
| 4 | `GlobalUnitStatus.robot_bullets`（字段 12）两版都未写明元素个数 | 保持 `repeated int32` 不定长，不假设 4 个 |
| 5 | 2027 概览表说「步兵/重装 性能体系状态同步」，正文 2.2.24 说「步兵…」 | 字段/proto 不变，按正文语义实现；概览表疑为机械替换遗留 |
| 6 | 2027 全 PDF 页脚仍印「© 2026 大疆版权所有」 | 排版瑕疵，不影响条款 |
| 7 | 2027 V1.0.0 修改日志仅「首次发布」，未记录任何删除/改动项 | 变更范围由结构比对得出（见对比报告） |

**与版本无关、保持不变的实现约定**：topic = 消息名（不带 package 前缀）、payload = protobuf 二进制、
`qos=1`、Protobuf v3（≥ 3.15）、MQTT `192.168.12.1:3333`、图传 UDP `3334`、8 字节大端包头、单包 1400B。
