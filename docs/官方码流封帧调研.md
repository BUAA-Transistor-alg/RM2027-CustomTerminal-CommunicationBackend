# 官方图传码流「封帧方式」调研

**目的**：在实现「C++ 内部编解码、两端只传图片」之前，先弄清官方码流到底怎么把 HEVC 数据切成一个个 UDP 包、
以及一个「帧编号」对应解码器视角下的什么单位。这决定了接收端怎么组帧、怎么喂解码器、以及要容忍哪些异常。

**结论先行**

| 问题 | 结论 | 依据 |
| :-- | :-- | :-- |
| UDP 包头 | 8 字节：帧编号(u16) + 分片序号(u16) + 当前帧总字节数(u32) | 官方 2027 V1.0.0 §2 明文（2026 V2.0.0 同） |
| 字节序 | **大端** | 官方 2027 V1.0.0 §2 明文：「此额外添加的 8 个字节为大端传输」 |
| 单包上限 | **1400 B**，负载 **1392 B** | 官方 2027 V1.0.0 §2 明文 |
| 重传 | **无重传机制** | 官方 2027 V1.0.0 §2 明文 |
| **一个「帧编号」= 什么** | **一个完整的 HEVC access unit（AU）** | 见 §2，社区实现一致 |
| 码流格式 | HEVC/H.265，**Annex-B**（起始码 `00 00 01` / `00 00 00 01`） | 官方 2027 V1.0.0 + 各实现按起始码解析 |
| 分片大小 | **对端可变**，接收端不能假设 | 各实现都按 `fragmentIndex` 定位而非固定偏移 |
| GOP | **可能很长** | SharkClient 源码注释 |
| 参数集 | 随 IDR **in-band 重复发送** | 各实现直接喂解码器、不额外注入 extradata |

## 1. 官方协议原文（RM2027 V1.0.0 §2）

> 此外，自定义终端可通过 udp 监听 3334 端口获取图传码流数据。图传码流数据的帧率为 60 帧，
> 分辨率为 1920\*1080，编码格式为 hevc，标准 h265 格式，无重传机制。
>
> 每个 udp 包的码流数据的前 8 个字节固定为：
> 帧编号（递增）：2 byte / 当前帧内分片序号：2 byte / 当前帧总字节数：4 byte
>
> **此额外添加的 8 个字节为大端传输。**
> 每个 udp 包最大为 1400 个字节，除去 8 个固定字节外，大小为 1392。

官方文档到此为止 —— **没有**说明「帧编号」对应解码视角的什么单位，也没说参数集怎么发。
这部分只能从社区实现反推。

> **版本校准**：以上图传段在 RM2026 V2.0.0（20260626）§2 与 RM2027 V1.0.0（20261029）§2 中**逐字相同**，
> 2027 未对封帧规则做任何调整；本文的结论对两版同时成立。

## 2. 「一个帧编号 = 一个 access unit」的证据

### 2.1 `JNU-SHARK/SharkClient`（Rust，同队重写版）

源码注释与实现都明确把「帧」当作 AU：

```rust
/// Maximum number of compressed H.265 access units queued for the background decoder.
/// Dependent codecs cannot drop arbitrary delta frames without losing decoder ...
const ...  // 有界 FIFO，元素是 AU
```

组帧完成后**原样**交给解码器，没有任何拼接或再切分：

```rust
if complete {
    if let Some(finished) = in_flight_frames.remove(&frame_number) {
        let info = detect_frame_type(finished.payload());
        ...
        let decode_result = d.decode_to_yuv(&pending.data);   // ← 直接喂
```

### 2.2 `ClearWei/RM26_Client`（C++/Qt）

其 `VideoReceiver.h` 的流程图同样写着：

```
│ 帧重组缓冲区 │ → 完整 HEVC NAL → │ 解码器 │
```

并注明「发送完整纯净的包进行解码」。

### 2.3 其余实现

`RMMock`（发送端）也是**每编码一帧 → 一个帧编号 → 分片发完**，与「帧 = AU」一致。

> **对本项目的含义**：接收端组出一个帧编号的完整字节后，应把它**当作一个 AU 直接投喂解码器**，
> 不要试图自己按 NAL 再切一遍；发送端则应保证**每个帧编号里放一个完整的 AU**
> （含该 AU 所需的参数集），这样与官方客户端的行为一致。

## 3. 官方流的编码特征（客户端必须容忍的情况）

### 3.1 GOP 可能很长
SharkClient 源码注释：

> Many real robot streams use long GOPs; waiting for the next IDR ...

推论与要求：
* 解码必须**从 IDR 开始**；中途接入或丢包后不能立即出图，要等下一个 IDR。
* 丢包（无重传）后解码器会报错 → **不能销毁重建**（SharkClient 注释：重建一次约 100 ms），
  应打标记 + 等下一个 IDR 自然重同步。
* 预览要显示「等待关键帧」状态。

### 3.2 参数集随 IDR 重复（in-band）
各实现都是把重组后的字节直接喂解码器、**没有额外注入 VPS/SPS/PPS 作为 extradata**，
说明参数集是在码流里跟着 IDR 一起到的。客户端不能假设「只在流开头发一次」。

### 3.3 码流格式未必是你预期的
* `RM26_Client` 同时内置了 **H.264 解码器**作为兜底；
* `SharkClient` 有独立的 `codec_detect` 模块，做 **JPEG / H.264 / H.265** 的 NAL 解析与关键帧探测。

推论：健壮的客户端应做**格式探测**（至少区分 H.265 / H.264 / JPEG），而不是盲目按 H.265 解。

### 3.4 分片与乱序
* 各实现都用 `fragmentIndex` 写入缓冲区对应位置，**不假设分片大小**；
* 需要处理：乱序到达、重复分片、帧号回绕、缺片导致的不完整帧、过期帧清理。

## 4. ⚠️ 文档之间的矛盾：分辨率

| 来源 | 分辨率 | 帧率 |
| :-- | :-- | :-- |
| 2027 通信协议 V1.0.0 §2（2026 V2.0.0 同） | **1920 × 1080** | 60 |
| VTM 图传模块用户手册（VT02/VT12） | **1280 × 720** | 60 |

两者不一致。可能的解释：协议里的 1920×1080 指的是**赛事引擎侧**提供给自定义终端的流，
而 VTM 手册描述的是机器人端相机图传模块的输出。也可能不同赛季/不同链路规格不同。

**结论：客户端绝不能写死分辨率**，必须按 SPS / 解码器实际输出自适应。
发送端（我们的模拟服务器）按协议给 1920×1080@60，但客户端要能吃任意分辨率。

## 5. 对实现的指导（本次改造直接采用）

### 接收端
1. 按 `fragmentIndex` 拼装，**不假设 MTU**；
2. 组出完整 AU → 投喂解码器；解码失败 → 打标记、**不重建解码器**、等下一个 IDR；
3. 做 **codec 探测**（H.265 / H.264 / JPEG），按探测结果选解码器；
4. 分辨率自适应，不写死；
5. 只保留**最新解码帧**（预览语义），UI 慢时丢旧帧，绝不阻塞网络/解码线程；
6. 统计要能反映异常：不完整帧、丢包、重复分片、乱序、解码错误、等待关键帧次数。

### 发送端（压力矩阵，专门用来搞客户端）
按用户要求，发送端要能覆盖尽量多的编码方式，用于验证客户端稳定性：

| 维度 | 取值 |
| :-- | :-- |
| B 帧 | 0 / 2 / 3（影响输出顺序与 AU 数量） |
| Slice 数 | 1 / 2 / 4（一个 AU 里多个 VCL NAL） |
| GOP 长度 | 1（全 IDR）/ 30 / 120（长 GOP）/ 300 |
| 参数集重复 | 每个 IDR 重复 / 只发一次 |
| AUD | 有 / 无 |
| Profile / 位深 | Main 8bit / Main10 10bit |
| 色度格式 | yuv420p / yuv422p / yuv444p |
| 分辨率 | 随输入 / 中途变化 |
| 分片大小 | 1392 / 1024 / 512 / 接近 MTU 上限 |
| 网络故障注入 | 丢包 / 乱序 / 重复分片 / 帧号回绕 |
| 帧率 | 60 / 30 / 120 |
| preset | ultrafast / veryfast / medium |

> 其中「B 帧 + 多 slice + 长 GOP + 参数集只发一次」的组合最容易打死客户端 ——
> 因为这要求客户端正确处理**解码顺序 ≠ 显示顺序**、**一个 AU 多个 NAL**、
> 以及**丢包后长时间无法恢复**。

## 6. 丢包后的解码策略（按真实数字图传的通行做法）

**不要冻结画面。** 操作手靠画面里的运动趋势判断往哪走，冻结等于让他失明。
这也和主流播放器/图传的做法一致。

### 6.1 标准做法：解码器尽量输出任何东西

mpv 从 2013 年起就默认打开 `CODEC_FLAG2_SHOW_ALL`，提交说明写得很直白：
播放器应该"尽可能输出任何东西"，包括关键帧之前的帧和已识别为损坏的帧
（[mpv commit 392856e](https://github.com/mpv-player/mpv/commit/392856ed4d86c71ecfb9b8036351ba2acd825a32)）。
对应到 FFmpeg 4.x 的两个标志：

| 标志 | 作用 |
| :-- | :-- |
| `AV_CODEC_FLAG_OUTPUT_CORRUPT` (1<<3) | 即使帧损坏也输出 |
| `AV_CODEC_FLAG2_SHOW_ALL` (1<<22) | 连"初始关键帧之前解出来的帧"也输出 |
| `err_recognition = AV_EF_IGNORE_ERR` | 遇到轻微错误不要中止解码 |

本项目接收端已按此设置。

### 6.2 丢包后画面会怎样（实测，已更正一处早期误判）

> **更正**：我最初看到"解码结果是一片均匀灰"，就归因为"参考帧缺失 ->
> FFmpeg 造灰色假参考 -> P 帧解出灰"。**这个解释是错的**。做了对照实验后确认：
> FFmpeg 的 HEVC 解码器**确实会使用之前的参考帧**（本项目的编码配置是 3 个参考帧），
> 偶发丢包只会让**局部**出错，画面整体还在。

**实验一：只丢 1 个 AU（640x360，keyint=30，3 参考帧）**

| 流 | 帧 10–14 的灰度标准差 |
| :-- | :-- |
| 完整流 | 65.3 / 65.3 / 65.3 / 65.3 / 65.3（真实画面） |
| 丢掉第 10 个 AU | 36.4 / 27.4 / 26.7 / 27.3 / 27.6（**画面还在**，局部有损） |

**实验二：按不同丢帧率丢 AU（标准差越小越接近灰屏）**

| 丢帧率 | 帧 0..11 的标准差 | 灰屏帧(std<10) |
| :-- | :-- | :-- |
| 25% | 65 65 65 43 44 43 22 8 9 6 7 7 | 13/20 |
| 33% | 65 65 21 14 9 10 7 8 7 7 7 7 | 16/20 |
| 50% | 65 34 12 6 5 5 5 5 5 5 5 5 | 13/20 |

结论：**偶发丢包无损观感，持续丢包会让画面逐帧衰减到灰**。机制是：
参考帧缺失时 FFmpeg 用灰色假参考（`generate_missing_ref`）顶上，
而这幅"灰图"又成了后续 P 帧的参考，误差沿参考链**逐帧累积**，
直到下一个 IDR 才复位。这是预测编码的固有性质，与解码器实现无关 ——
用 ffmpeg CLI 解同一段字节流，结果完全一致（逐一加
`output_corrupt` / `showall` / `low_delay` / `err_detect ignore_err` 都不改变结论）。

**实验三：对照实验，逐项打开本项目解码器用的标志**

```
默认             帧10..14 标准差 = 36.4 | 27.4 | 26.7 | 27.3 | 27.6
output_corrupt   ... 完全相同
show_all         ... 完全相同
low_delay        ... 完全相同
三个全开          ... 完全相同
err_detect ignore_err / careful ... 完全相同
```

→ 这些标志**不会**导致灰屏；它们只影响"要不要把解出来的东西交给你"。

### 6.2.1 实测：不同丢包率下的画面（1280x720@30，判据是像素级与合成图案比对）

| 丢包率 | 收帧/解码 | 画面平均绝对误差 |
| :-- | :-- | :-- |
| 0% | 61 / 61 | 1.65（几乎无损） |
| 约 2% | 59 / 59 | 1.65 ✅ |
| 约 4% | 57 / 57 | 1.65 / 106（有一张已衰减） |
| 约 8% | 53 / 53 | 106 / 106 / 106（全部衰减） |

注意 **解码帧数始终等于收帧数** —— 客户端在任何丢包率下都**没有冻结**，一直在出图。

### 6.2.2 所以真正的结论

1. 客户端策略：**照常解码、照常显示，绝不冻结**（已实现）。
2. 偶发丢包（个位数百分比）下画面基本无损，**这与真实局域网链路相符**。
3. 持续高丢包（>5%）下画面会衰减到灰 —— 这是编码层的问题，
   靠解码端任何技巧都救不回来，只能靠**降码率/降分辨率、缩短 GOP、intra-refresh、
   或链路层 FEC/重传**。本项目压测里注入的 14%~33% 丢帧远超真实链路。

### 6.3 编码端：用 intra-refresh 代替周期性 IDR

低延迟链路（无人机图传、远程驾驶）的通行做法是**不用大 IDR，改为周期性
intra-refresh**：每帧插入若干列 I 宏块/CTU，整幅画面在一个刷新周期内自愈，
既避免了 IDR 的码率尖峰，也让丢包后能在数帧内恢复
（[US20220264130A1](https://patents.google.com/patent/US20220264130A1/)、
[LTE 远程驾驶](https://ar5iv.labs.arxiv.org/html/2209.09794)："we have chosen columns
of I-macroblocks ... as the granularity of intra refresh"）。

x265 支持：`intra-refresh=1`。实测它的副作用（x265 自己会警告）：

* 强制 `max_num_references = 1`
* 与 open-GOP 不兼容（自动关闭）
* 关闭 scenecut
* **刷新周期 = keyint**，所以 keyint 要按"期望恢复时间"来设，而不是按传统 GOP 长度

本项目的编码器已支持 `EncoderConfig::intraRefresh`。

### 6.4 还没定的事（需要拍板）

上面 6.2 那个"整幅灰图"到底怎么显示，有三种做法，各有取舍：

| 做法 | 操作手看到 | 代价 |
| :-- | :-- | :-- |
| A. 照原样显示灰图 | 灰屏，无信息 | 最诚实，但丢包期间完全没用 |
| B. 检测到整帧不可恢复时，保留上一帧好画面 | 短暂定格，随后自愈 | 需要判断"这帧可不可信"；定格期间无运动信息 |
| C. 显示解码结果，但在画面上叠加降级提示 | 灰/花屏 + 明确警示 | 需要 UI 叠加，且灰屏依旧无信息 |

FFmpeg 对"未能完整恢复"的帧会设置 `AV_FRAME_FLAG_CORRUPT`（见
[ffmpeg-devel 补丁](http://lists.mplayerhq.hu/pipermail/ffmpeg-devel/2015-December/184712.html)），
理论上 B 做法有依据可判。但官方协议本身没有重传/FEC，
真实链路的丢包率应该远低于我们压测注入的 14%。
